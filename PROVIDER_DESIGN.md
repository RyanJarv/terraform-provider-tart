# Terraform provider design for Tart

The `tart_vm` resource manages a named VM in the Tart store selected by the provider. The `tart_vm` data source reads one. This guide records Terraform conventions and the design choices they leave to this project. The [VM resource reference](docs/resources/vm.md#lifecycle) describes current behavior.

## Schema and provider configuration

- **Describe who sets each value.** Use `Required` for inputs the user must supply and `Computed` for observations such as guest OS. Use `Optional` with `Computed` when the user can supply a value and the provider chooses one if omitted. A generated VM name fits that last case. Document units and what each value measures, especially saved memory in MiB and virtual disk capacity in GB. [Framework attributes](https://developer.hashicorp.com/terraform/plugin/framework/handling-data/attributes)
- **Distinguish omitted from unknown.** An omitted store can use the documented default. A store path supplied by an unresolved expression may eventually point somewhere else. In that case, falling back to the default could operate on the wrong VMs. Configure the client once per provider configuration and pass it to both resources and data sources so provider aliases can select different stores. [Framework providers](https://developer.hashicorp.com/terraform/plugin/framework/providers) · [Tart provider configuration](provider/internal/provider/provider.go)
- **Validate where the user can act on the error.** A known `cpu_count = 0` can be rejected during configuration validation, even without access to Tart. Attach the diagnostic to `cpu_count`. Defer checks requiring an unknown input until it resolves, and recheck live conditions before writing. Reject invalid known sizes before a destroy-first replacement can remove the existing VM. [Framework validation](https://developer.hashicorp.com/terraform/plugin/framework/validation) · [Diagnostics](https://developer.hashicorp.com/terraform/plugin/framework/diagnostics)

## Identity and import

**Naming recommendation.** Allow an exact VM name, or generate one when omitted. An optional prefix gives generated names a recognizable purpose. Generate once per VM creation, persist the result, and use it for subsequent reads and import. A fresh generated name lets the old and new VM coexist during `create_before_destroy`; an exact name already in use cannot do that. Today this provider requires an exact name. HashiCorp's IAM role implementation demonstrates both naming styles. [IAM role creation](https://github.com/hashicorp/terraform-provider-aws/blob/386e9b920ec2323b9bf11741e287a84549e08957/internal/service/iam/role.go#L219) · [Terraform replacement order](https://developer.hashicorp.com/terraform/language/meta-arguments/lifecycle#create_before_destroy)

Tart looks up a VM by name within a store. A user who knows the store and the name should be able to import the VM. Import needs to seed enough state for the subsequent `Read` to refresh it. Seed the name during import and let the normal read populate observed fields. Importing a VM gives us no evidence about which image created it. [Framework import guidance](https://developer.hashicorp.com/terraform/plugin/framework/resources/import)

The Plugin Framework allows a resource to omit a public `id` attribute. Terraform 1.12+ also supports an optional structured resource identity, which must uniquely identify an object across provider instances. For local VMs, the same name can exist in different stores, and the same absolute store path can exist on different Macs. An identity design needs to state its scope. [Framework ID guidance](https://developer.hashicorp.com/terraform/plugin/framework/acctests#no-id-found-in-attributes) · [Resource identity](https://developer.hashicorp.com/terraform/plugin/framework/resources/identity)

For Tart, the public `id` is the local VM name. All operations target that name in the configured store, even if someone recreated the VM outside Terraform. AWS IAM roles likewise use the role name for lookup. [AWS IAM role](https://github.com/hashicorp/terraform-provider-aws/blob/386e9b920ec2323b9bf11741e287a84549e08957/internal/service/iam/role.go#L274-L303)

## Refresh and deletion

| What the provider observes | Recommended behavior |
| --- | --- |
| The VM exists and its CPU or memory configuration changed. | Refresh the observed values. Terraform can then plan how to reconcile them. |
| A lookup confirms the managed VM is absent from the intended store. | On resource refresh, call `RemoveResource`. A configured clone can then be recreated. On delete, absence already satisfies the request. A data source lookup should report the missing VM. |
| The lookup fails because of permissions, malformed output, or an inaccessible store. | Return a diagnostic and preserve state. The VM may still exist. |
| A different VM occupies the recorded name. | Refresh from the VM at that name. |

Destroy and replacement both call Tart by name. Operators can protect a configured VM with Terraform’s `prevent_destroy`. [Framework read guidance](https://developer.hashicorp.com/terraform/plugin/framework/resources/read#recommendations) · [Framework delete guidance](https://developer.hashicorp.com/terraform/plugin/framework/resources/delete#recommendations)

## Concurrency

Terraform expects each managed object to be bound to one resource address. Operators who want to reference a VM from another project can use the data source there. Backend state locking protects concurrent access to a particular state. Separate states and direct Tart commands can still reach the same store. [Import ownership convention](https://developer.hashicorp.com/terraform/cli/commands/import#usage) · [State locking](https://developer.hashicorp.com/terraform/language/state/locking)

The store-wide lock serializes cooperating provider writes, including cloning and configuring a new VM before reading it back. Direct Tart commands bypass the lock. Before changing its scope, identify which supported operations share a VM or store. Google’s IAM resources use a policy-specific lock when editing a shared policy. [Provider write lock](provider/internal/provider/store_lock.go) · [Google IAM policy update](https://github.com/hashicorp/terraform-provider-google/blob/2bf2f3df3eadb26bc193bce13beddf857fcd9e8b/google/tpgiamresource/iam.go#L109-L131)

## Plan, apply, and recovery

- Express unconditional replacement rules on the relevant schema attributes with `RequiresReplace`. Validate known inputs during planning. Test an immutable attribute fed by an upstream output: resolving it during apply must be consistent with the action Terraform showed the user. [Framework plan modification](https://developer.hashicorp.com/terraform/plugin/framework/resources/plan-modification)
- Define CPU and memory as saved Tart settings. Apply them in place, read them back, and expect an empty subsequent plan. Restart timing belongs to the operator. [VM lifecycle](docs/resources/vm.md#lifecycle)
- Reject an occupied clone destination. If cloning succeeds and a later step fails, preserve enough information to identify the verified clone and explain how to recover it. If the clone is present but absent from state, the user can import it by name. [Framework create guidance](https://developer.hashicorp.com/terraform/plugin/framework/resources/create#caveats)

## How other providers handle these cases

These examples use SDKv2-style resource handlers. In the Plugin Framework, write response state explicitly and use `RemoveResource` on confirmed absence during refresh. Copying a call to `SetId` would miss the lifecycle behavior the example illustrates.

| Case | Released provider behavior | Implication for Tart |
| --- | --- | --- |
| Name reuse | Google Compute addresses a VM by project, zone, and name. It separately records the service's numeric `instance_id`. [Google v8.12.0 creation](https://github.com/hashicorp/terraform-provider-google/blob/v8.12.0/google/services/compute/resource_compute_instance.go#L2044-L2053) · [Instance ID readback](https://github.com/hashicorp/terraform-provider-google/blob/v8.12.0/google/services/compute/resource_compute_instance.go#L2373-L2376) | Store and name suffice for lookup. Reusing a name reuses that lookup. |
| An occupied name or an already-deleted VM | Azure's Linux VM checks for an existing object on its normal create path and reports that it needs import. Delete returns success if its initial lookup confirms absence. [AzureRM v5.14.0 create](https://github.com/hashicorp/terraform-provider-azurerm/blob/v5.14.0/internal/services/compute/resources/linux_virtual_machine/r_create.go#L31-L49) · [Delete](https://github.com/hashicorp/terraform-provider-azurerm/blob/v5.14.0/internal/services/compute/resources/linux_virtual_machine/r_delete.go#L31-L50) | Surface the collision before cloning. Once absence in the intended store is confirmed, a delete retry has achieved its goal. |
| Concurrent writes | Azure locks Linux VM updates by VM name and resource type. [AzureRM update](https://github.com/hashicorp/terraform-provider-azurerm/blob/v5.14.0/internal/services/compute/resources/linux_virtual_machine/r_update.go#L28-L38) | A narrower lock has precedent. Before changing Tart's cross-process store lock, account for clone operations that read one VM and write another. |
| Failure after successful creation | Kubernetes records a Deployment's ID immediately after the API accepts creation, before waiting for rollout. A rollout timeout returns an error after that point. [Kubernetes v3.5.0 creation](https://github.com/hashicorp/terraform-provider-kubernetes/blob/v3.5.0/kubernetes/resource_kubernetes_deployment_v1.go#L251-L271) | Report the name of a partially configured clone so the user can inspect and import it. |
| Destructive actions and restart consent | Google Compute asks users to apply removal of deletion protection separately before destroy. For updates requiring a stop, it checks whether the user permitted downtime. [Google deletion guard](https://github.com/hashicorp/terraform-provider-google/blob/v8.12.0/google/services/compute/resource_compute_instance.go#L4113-L4116) · [Stop consent](https://github.com/hashicorp/terraform-provider-google/blob/v8.12.0/google/services/compute/resource_compute_instance.go#L3515-L3530) | Tart delegates deletion protection to Terraform’s lifecycle. A Tart CPU or memory configuration write requires no automatic restart. |

## Testing and upgrades

- **Test what a practitioner sees.** The lifecycle suite already applies saved plans, introduces CPU drift, imports a VM, and replaces the VM at a name between plan and apply. The highest-value regression cases to add are a name supplied by an upstream output (apply follows the planned action), and a verified clone followed by a failed configuration write (the documented recovery works). Use a fake Tart executable to make that last failure repeatable. [Project lifecycle test](tests/lifecycle.sh) · [Framework acceptance tests](https://developer.hashicorp.com/terraform/plugin/framework/acctests)
- **Choose which old states to support.** When changing a stored schema incompatibly, each supported prior schema version needs a direct upgrade to the current one. Test with serialized prior state. Schema version 2 upgrades versions 0 and 1 by using the stored VM name as the ID and dropping the former deletion flags. Once published, document breaking changes and the recovery or migration path alongside the release. [Framework state upgrades](https://developer.hashicorp.com/terraform/plugin/framework/resources/state-upgrade) · [Release procedure](RELEASING.md)

HashiCorp's HashiCups tutorials show how to pass a configured client to both resources and data sources and verify imported state. For Tart, compare the fields import can recover, such as CPU and memory, and verify that an imported VM follows the same delete behavior as a clone. To catch the computed-name regression, assert the planned action as well as the final settings. The existing CLI suite can check a saved plan; HashiCorp's testing library also provides `ExpectResourceAction`.
